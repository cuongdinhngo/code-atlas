# R2.4 anchor-vocabulary denylist — SHA-256/16 of each banned token, lowercased (task 325).
#
# WHY HASHES AND NOT NAMES. The sibling file `framework_denylist.txt` lists `laravel`, `react` in
# the clear because those are public names. This list is the opposite: it holds the identifiers of
# a private client codebase, so writing them here would publish exactly what the guard exists to
# keep out. A plaintext denylist of secrets is the leak.
#
# THIS IS OBFUSCATION, NOT SECRECY — stated plainly so no one relies on more than it gives. The
# entries are short, unsalted digests of real words; anyone who already suspects a term can confirm
# it by hashing their guess. What this buys is that the repo never *hands over* the vocabulary, and
# that a reader who does not already know it cannot learn it here. Salting would break CI, which
# must reproduce the digests from this file alone.
#
# THE PLAINTEXT MAPPING IS NOT IN THIS REPO, by design. It lives with the maintainer. When the
# guard fires it prints the digest, not the word; look the digest up in that local map.
#
# TO ADD A TERM (do this in a shell, never by pasting the word into a tracked file):
#     python3 -c "import hashlib,sys;print(hashlib.sha256(sys.argv[1].lower().encode()).hexdigest()[:16])" 'TheTerm'
#
# Only whole, distinctive tokens belong here. A term that is also ordinary English — `resident`,
# `aus`, `nz` — must NOT be added: it would fire on every honest use. Those were handled by
# replacement instead, and the structural patterns in `tests/test_no_client_identifiers.py` cover
# the shapes (tracker keys, corporate domains, host paths) that no word list can.
#
# Consumers derive their check from this file alone: ci.yml, scripts/gate.sh, and
# tests/test_no_client_identifiers.py. Lives under tests/ so `tests/` being unswept by R2.2 (R2.3)
# cannot make it self-match.
